# Журнал проблем и трудностей (problem log)

Журнал фиксирует трудности, возникшие при разработке frontend, способы их решения и оставшиеся риски.

---

## [2024 — Этап 1] Node.js не установлен в системе

- **Проблема**: `node`, `npm`, `npx`, `winget`, `scoop`, `choco` отсутствуют в PATH — невозможно инициализировать Vite-проект стандартным способом.
- **Решение**: скачал портативную сборку Node.js v20.18.1 (zip с nodejs.org), распаковал в `%TEMP%\node-portable` и подключил к PATH в каждой команде терминала.
- **Остаточный риск**: PATH действует только в рамках сессии терминала; папка в `%TEMP%` может быть очищена системой. Рекомендуется системная установка Node 20 LTS. Также была выдана ошибка `EBADENGINE` (eslint-visitor-keys требует node ^20.19.0) — только предупреждение, работоспособность не нарушена.

## [Этап 1] Шаблон Vite создал проект не на том стеке

- **Проблема**: `npm create vite@latest` (create-vite@9) сгенерировал проект на React 19 + Vite 8 + oxlint, тогда как по `AGENTS/frontend developer.md` требуется React 18 + Vite 6 + ESLint. Плюс `EBADENGINE`-предупреждения из-за engine-требований шаблона.
- **Решение**: вручную привёл `package.json` к целевому стеку (react/react-dom ^18.3, vite ^6, typescript ~5.7, eslint 9 + typescript-eslint + плагины react-hooks/react-refresh), заменил `lint: oxlint` на `eslint .`, удалил `.oxlintrc.json`-подход из скриптов.
- **Остаточный риск**: нет — после переустановки зависимостей всё совместимо.

## [Этап 1] Несовместимые опции TypeScript из шаблона

- **Проблема**: шаблонные `tsconfig.app.json` и `tsconfig.node.json` использовали опции `erasableSyntaxOnly` (поддерживается только в TS 6) и `types: ["node"]` без установленного `@types/node`; после даунгрейда до TS 5.7 — ошибки компиляции (`TS5023`, `TS2688`, `TS2792` — неразрешение модулей в `vite.config.ts`).
- **Решение**: удалил `erasableSyntaxOnly` и `types: ["node"]`; в `tsconfig.node.json` выставил `module: esnext` + `moduleResolution: bundler`.

## [Этап 1] Ограничение инструмента правки при перезаписи файлов

- **Проблема**: при замене шаблонного `src/App.tsx` (счётчик Vite) на демо-страницу — правки по частям дважды оставили «хвост» старого кода (вложенные объявления `function App`, дубли `export default App`), из-за чего `tsc` и esbuild выдавали синтаксические ошибки.
- **Решение**: дочитал файл, поэтапно удалил остатки шаблонного JSX якорными правками; файл стал чистым демо-компонентом.
- **Вывод**: шаблонные файлы лучше заменять одним цельным коммитом контента сразу после создания, а не последовательными правками.

## [Этап 1] Headless-браузер недоступен — визуальная проверка не выполнена

- **Проблема**: запуск `npx vite` и browser-automation (headless Playwright) в среде завершался таймаутом (120 с) без вывода — проверить рендер демо-страницы в браузере не удалось.

- **Остаточный риск**: рендер демо-страницы и иконок визуально не подтверждён. Проверка перенесена на Этап 10 (визуальный QA по `design.png`).

## [Этап 2] Дублирование стилей при рефакторинге (потерян CSS-класс)

- **Проблема**: при выделении `PanelRestoreBar` в отдельный компонент класс `.panel-restore-bar--right` (бордер слева, для правой панели) остался в JSX, но его CSS был удалён вместе с блоком из `AppShell.css` — правая полоса возврата потеряла бы отличия и выглядела как левая.
- **Решение**: создал `PanelRestoreBar.css` с модификатором, добавил импорт в компонент; обнаружил через `grep` по всем `className` после разнесения стилей.
- **Вывод**: при выносе компонента в отдельный файл нужно переносить ВСЕ его CSS-модификаторы, а не только базовый класс; полезно проверять пару «класс в JSX ↔ селектор в CSS».

## [Этап 2] Grid-колонки для разделителей (sash)

- **Проблема**: при добавлении `PanelResizer` как отдельного grid-элемента он не был учтён в `grid-template-columns` — раскладка ломалась (5-я колонка с auto-шириной сжимала карту).
- **Решение**: колонки рассчитываются в компоненте динамически (`activity | left | 6px | 1fr | 6px | right`), sash добавляется в шаблон только когда панель развёрнута и доступен `onWidthChange`.
- **Вывод**: при рендере дополнительных grid/flex-элементов синхронно обновлять их учёт в шаблоне раскладки.

## [Этап 2] Устаревшее состояние `useState`-дефолтов при смене требований

- **Проблема**: за Этап 2 ширина панелей менялась трижды (340/380 → 280 → 100 → 180) — при каждом изменении пришлось бы править и лимиты, и дефолты, и fallback в `AppShell`; легко рассинхронизировать.
- **Решение**: дефолт панелей привязан к константе (`DEFAULT_PANEL_WIDTH`), `clampWidth()` гарантирует границы в одном месте (`panelWidth.ts`), а не в разрозненных местах.
- **Вывод**: одиночные источники констант и валидация в одной функции предотвращают рассинхрон при итерациях требований.

## [Этап 2] Использование pointer events + setPointerCapture для drag

- **Проблема**: классический подход (`onMouseMove` на документе, `onMouseUp` где угодно) сложен и легко ломается (теряются события при выходе за окно, конфликты с text-selection).
- **Решение**: Pointer Events с `setPointerCapture` на элементе-разделителе — события гарантированно доставляются даже за пределами окна; слушатели добавляются на `pointerdown` и снимаются на `pointerup`/`pointercancel`; выделение текста подавлено через `user-select: none` на shell во время drag (CSS `:has(...[data-dragging='true'])`).
- **Остаточный риск**: поддержка `:has()` — все современные браузеры (Chrome 105+, Safari 15.4+, Firefox 121+); для legacy-браузеров fallback не критичен (это только cursor/user-select во время drag).

## [Этап 3] Активный индикатор не сбрасывался при повторном клике

- **Проблема**: клик по уже активному пункту вызывал лишний re-render и подчистка индикатора требовала синхронизации `activeModule` между `App.tsx` и `ActivityBar` (props drilling).
- **Решение**: `activeModule` — единственный источник истины в `App`, `ActivityBar` — контролируемый компонент (`items` + `active` + `onChange`); повторный клик игнорируется ранним return.
- **Вывод**: UI-состояние верхнего уровня держать наверху, компоненты делать полностью управляемыми.

## [Этап 4] Рекурсивное дерево: общий `key` и «замыкание» обработчиков на неверный узел

- **Проблема**: при рекурсивном рендере `ObjectTreeGroup → ObjectTreeSubGroup → ObjectTreeNode` ключи по индексу массива приводили к тому, что при сворачивании групп состояние «переползало» на соседние узлы; обработчики `select`/`toggle-visibility`, объявленные inline с обращением к `node.id` переменной цикла, в ряде мест ссылались не на тот узел.
- **Решение**: `key={node.id}` (id стабильны), обработчики принимают `id` как параметр, а не захватывают переменную; состояние раскрытия вынесено в один `expandedIds: Set<string>` на уровне `ObjectTree`.
- **Вывод**: в рекурсивных деревьях — только стабильные ключи и параметризованные колбэки; состояние раскрытия централизовать, а не хранить в каждом узле.

## [Этап 4] Кнопки быстрых действий перехватывали клик выделения узла

- **Проблема**: кнопка диаграммы и глаз видимости находились внутри строки-узла; клик по ним одновременно выделял узел (bubbling до обработчика строки).
- **Решение**: на кнопках `e.stopPropagation()` + `type="button"`; события узла (`select`, `open-diagram`, `toggle-visibility`) оставлены раздельными, как в контракте `ObjectTreeNode`.
- **Вывод**: вложенные интерактивные элементы всегда требуют stopPropagation и явных event-контрактов.

## [Этап 5] Тумблеры и радио были неассессибил-совместимы

- **Проблема**: первый вариант `ui-switch` и `BasemapSelector` был на div/label с произвольным UI — не работал с клавиатуры, состояние не считывалось скринридерами.

- **Вывод**: кастомные контролы строить поверх нативных input/role-атрибутов, а не вместо них.

## [Этап 6] Пакет `@vis-network/react` недоступен — нужен был кастомный хук

- **Проблема**: в README-плане значился `@vis-network/react`, но этот пакет недоступен (не публикуется/не совместим), а ставить MapView на альтернативный стек нельзя — принято решение использовать `vis-network` напрямую.
- **Решение**: написал собственный хук `useVisNetwork` (инициализация `Network` на ref-контейнере, уничтожение в cleanup, обновление опций/data через effects), данные — `vis-data` (`DataSet`).
- **Остаточный риск**: хук не покрыт реальными сценариями resize-observability (vis-network делает это сам), но реакция на изменение размеров контейнера проверена только статически — перенесено в Этап 10.

## [Этап 6] Конфликт CSS vis-network с нашей сеткой и подложками

- **Проблема**: canvas vis-network рисует собственный фон; наша «сетка-план» через `::before` на контейнере и фоны подложек (`--bg-map-topo/--bg-map-satellite`) перекрывались или канвас их закрашивал; также коллизия imён классов (`.map-viewport__canvas` vs внутренние классы vis).
- **Решение**: фон подложек оставлен на контейнере (canvas прозрачный по умолчанию), сетка — на `::before` c `pointer-events: none`; все стили изолированы под `.map-viewport`; `data-basemap` на контейнере переключает подложку без реинициализации сети.
- **Остаточный риск**: прозрачность фона canvas зависит от опции `background` в vis — если позже включим фон в опциях сети, подложки нужно будет переносить в неё же.

## [Этап 6] Типы событий/опций vis-network и «мерцающая» реинициализация

- **Проблема**: naive-подход «при любом изменении props пересоздавать Network» приводил к мерцанию графа и потере позиции камеры; также типы `Options` в vis-network требуют приведения (`as Options`), часть полей опциональна в рантайме, но обязательна в типах.
- **Решение**: Network создаётся один раз на mount; изменения данных идут через `DataSet.update`/`add`/`remove`, изменения опций — через `setOptions`; `data-basemap` и стили — вне сети. В хуке опции собираются в `useMemo`, типы выровнены локальным `MapOptions`.
- **Вывод**: императивные canvas-библиотеки не «ререактятся» — их состояние (камера, позиция) живёт вне React, поэтому инициализировать один раз и менять инкрементально.

## [Этап 7] Модалка не видела имя объекта — поиск по дереву vs по графу

- **Проблема**: `MapDiagramModal` требует имя объекта («Северный»), но при открытии диаграммы из дерева доступен только `targetEntityId`; в мок-данных дерева (`TreeNodeData`) и карты (`mapData.ts`) объекты имеют разные структуры — простым обращением к полю имя не достать. Первая попытка дублировать поиск в самой модалке рассинхронизировала источники.
- **Решение**: создал функцию `findTreeNode(id)` в `mockData.ts` дерева — единая точка поиска имени по id; модалка принимает `entityName` строкой, поиск выполняет родитель (`App`), где известны оба источника данных.
- **Вывод**: не тянуть в листовый компонент знание о структуре данных — резолвить сущности выше по иерархии.

## [Этап 7] Размытие клика фоном модалки и z-index внутри зоны карты

- **Проблема**: модалка «плавающая» (floating-оверлей внутри зоны карты, а не fullscreen): при `position: absolute` она вставала под DOM-оверлеями бейджей рёбер (у них свой `z-index` из Этапа 6), а клики по фону одновременно попадали в сеть (drag карты начинался под модалкой).
- **Решение**: `z-index` оверлеев карты вынесен в общую шкалу переменных (`--z-badges` < `--z-modal`); фон модалки — прозрачный перехватчик кликов (`pointer-events: auto`, `stopPropagation`), а сама модалка позиционируется относительно контейнера `MapViewport`.
- **Остаточный риск**: шкала z-index сейчас в двух CSS-файлах; при добавлении новых оверлеев стоит вынести в `styles.css` токенами.

## [Этап 8] Коллизия имён: `InspectorTabBar` экспортировал типы и реестр из разных файлов

- **Проблема**: реестр вкладок `INSPECTOR_TABS` сначала оказался внутри компонента `InspectorPanel.tsx`, а типы `InspectorTabId` — в `types.ts`; `InspectorTabBar` не мог ссылаться на реестр без циклического импорта (Panel → TabBar → Panel).
- **Решение**: вынес реестр и тип `InspectorTab` в отдельный `tabs.ts` (реестр `INSPECTOR_TABS`, иконки `tab-*` по `icons.md`); `InspectorPanel` только потребляет, компоненты не импортируют друг друга циклично.
- **Вывод**: реестры/конфигурации держать в отдельных модулях выше компонентов — это и позволило типу `IconName` поймать несуществующие иконки `tab-*` на этапе компиляции.

## [Этап 8] Секции «Общие параметры» / «Состояние модели» не работали для разных типов объектов

- **Проблема**: мок-детали разных объектов (куст, УПН, точка поставки, трубопровод) имеют разный набор полей; наивные `entity.name`-обращения роняли strict-типизацию, а жёсткий единый набор PropertyRow показывал пустые строки для трубопроводов.
- **Решение**: `EntityDetails` описан как discriminated union по `kind`; `SectionGeneralParams` рендерит строки по конфигурации полей для каждого `kind` (трубопровод — длина, флюид вместо ЛУ/владельца), пустые значения скрываются, а не показываются `—`.
- **Вывод**: доменные union-типы вместо «одного большого интерфейса с опциональными полями» исключают целые классы ошибок рендера.

## [Этап 9] Зацикливание агента: повторные чтения без продвижения по задаче

- **Проблема**: при интеграции глобального UI-state (`useUiState`) и react-query в `App.tsx` — после сжатия истории диалога (контекстного саммари) — работа остановилась: несколько раз подряд выполнялось чтение одного и того же фрагмента `uiState.tsx` с одинаковыми аргументами вместо перехода к следующему шагу (правка `App.tsx`, сборка зон). В файле `App.new.tsx` остался недописанный placeholder (`useUiState?._left ?? []`), после которого работа оборвалась. Задача не продвигалась, хотя данные уже были получены.
- **Решение**: остановить цикл, явно восстановить план: перечитать файлы (`App.tsx`, `App.new.tsx`, `uiState.tsx`) одним заходом, затем завершить `App.tsx` цельной правкой (подключение `useUiState`, `AppShell`, `ActivityBar`, `LeftSidebar`, `MapViewport`, `InspectorPanel`, `useEntityDetailsQuery`), после чего прогнать `tsc -b` и `eslint .`.
- **Вывод**: после обрезки/сжатия контекста нельзя опираться на «интуитивное» состояние задачи — нужно первым шагом явно восстановить план (что готово / что осталось) и переходить к действиям, а не перечитывать уже известные файлы. Каждый шаг должен менять состояние проекта, иначе это трата итераций впустую.
- **Остаточный риск**: `App.new.tsx` — черновик с невалидным кодом; его нужно либо удалить после переноса содержимого в `App.tsx`, либо не включать в коммит, чтобы не ломать сборку (`tsc`).

## [Этап 11 — Вариант 2] Баг: рёбра не видны на гео-карте (метры вместо lng/lat)

- **Проблема**: при построении трубопровода/сегмента на чистой карте линии не отображались.
  Объекты и точки рисовались, а рёбра — нет.
- **Причина**: в `GeoGraphLayer` рёбра конвертировались через `toScreen(s.from.x, s.from.y, camera)`,
  но `toScreen` ожидает **lng/lat**, тогда как `from.x/from.y` — это **мировые единицы графа
  (метры)**. `lngLatToWorldPixel(метры, метры, zoom)` уносил точки далеко за пределы карты,
  и `<line>` рисовался вне видимой области. Объекты использовали `toScreen(v.lng, v.lat, camera)`
  (градусы) — поэтому были видны.
- **Решение**: рёбра переведены на `graphPointToScreen(s.from, camera)` (метры → экран),
  уже использовавшийся в ghost/анимации потоков. `toScreen` (lng/lat) оставлен для
  объектов/тройников/врезок.
- **Вывод**: в Варианте 2 модель хранит ДВА вида координат — lng/lat (для объектов) и мировые
  единицы/метры (для концов рёбер). Нельзя путать конвертеры: `toScreen` (lng/lat) ↔
  `graphPointToScreen` (метры).
- **Проверка**: `npm run build` и `npm run lint` — без ошибок. Визуально не проверялось
  (headless-браузер недоступен), но типовая ошибка устранена.

## [Этап 11 — Вариант 2] Баг: ПКМ создавала элемент при активном тройнике/врезке

- **Проблема**: при активном инструменте «Тройник»/«Врезка» правый клик создавал элемент,

  кнопки не порождают клик-создание. ПКМ теперь только завершает режим (через `contextmenu`).
- **Вывод**: различать кнопки мыши нужно СИМЕТРИЧНО — и в `pointerdown`, и в `pointerup`;

## [Этап 11 — Вариант 2] Вершины «исчезали» при отдалении карты (зум < 14)

- **Проблема**: при уменьшении зума (примерно < 14) объекты-вершины визуально
  «не прорисовывались»/терялись.
- **Причина**: размер объектов задан в МЕТРАХ (`MapVertex.w/h`), а на экране считается
  как `w × pxPerMeter(zoom)`. При малом зуме `pxPerMeter` крошечный, и реальный размер
  падал до ~5–8 px. Элемент выживал лишь за счёт CSS `min-width/min-height: 10px`, но
  подпись (11px, `white-space: nowrap`) не влезала и перекрывала соседей — объекты
  выглядели «пропавшими»/кашей.
- **Решение**: в `GeoGraphLayer` добавлен минимальный ЭКРАННЫЙ размер объекта
  `MIN_VERTEX_SCREEN_PX = 18`: если рассчитанный размер меньше, объект рисуется компактным
  маркером 18×18 (класс `is-tiny` — круглый, без подписи). Объект остаётся видимым и
  кликабельным на любом зуме, как маркеры в ГИС.
- **Вывод**: размеры «в метрах» надо ограничивать снизу по экрану — привязка к гео-масштабу
  без минимального экранного размера приводит к визуальному исчезновению объектов.
- **Проверка**: `npm run build` и `npm run lint` — без ошибок. Визуально не проверялось.

## [Этап 11 — Вариант 2] Надёжный снап концов рёбер к врезкам/тройникам

## [Этап 12] Перетаскивание и отсоединение конца ребра, привязанного к врезке/тройнику

## [Интеграция] Баг: HTTP 500 при сохранении графа (дубли id → unique-constraint) — ИСПРАВЛЕНО

- **Симптом**: кнопка «Сохранить» → «Не удалось сохранить граф: HTTP 500».
- **Причина** (из логов backend): `IntegrityError: duplicate key value violates unique
  constraint "uq_segment_project_external" — Key (project_id, external_key)=(…, seg-…)`.
  В payload сохранения попадали ДВЕ записи с одинаковым id (одно ребро/объект в
  состоянии дважды), и `save_map_graph` падал на unique-constraint по `external_key`.
- **Решение (с двух сторон)**:
  - Frontend (`api/mapSave.ts`): `dedupeById(...)` — объекты, сегменты и трубопроводы
    дедуплицируются по id перед отправкой;
  - Backend (`services/graph_import.py`): `_dedupe_by_id(...)` для ВСЕХ секций payload
    (facilities/nodes/segments/pipelines/licence_areas) — защита на стороне сервера,
    чтобы некорректный ввод давал валидный результат, а не 500.
  - Тест `test_save_dedupes_duplicate_ids` — сохранение с дублями проходит, дубль
    отбрасывается (facilities=1). Всего **12 тестов OK** на PostgreSQL.
- **Проверка**: тот же запрос с дублем теперь → 201, `counts {facilities:1, …}` (было 500).
- **Замечание**: сообщения `Unable to preventDefault inside passive event listener` в
  консоли — от wheel-обработчика (не связаны с сохранением, безвредны).

## [Этап 12] Удаление врезки сшивает разбитое ею ребро обратно

## [Этап 12] Сшивание ребра при удалении врезки: логика вынесена и ПРОВЕРЕНА фактически

- **Задача**: удаление врезки должно возвращать разбитое ею ребро в исходное единое
  состояние (два сегмента → один).
- **Что сделано**:
  - логика вынесена в **чистую функцию** `features/map/healSplits.ts`
    (`healRemovedTaps(segments, removedTapIds)`) — без React, легко проверяется и
    тестируется в изоляции;

  - правило сшивания: если через удаляемую врезку соединены РОВНО ДВА сегмента —
    они заменяются ОДНИМ (от свободного конца A до свободного конца B); если
    подключено 3+ сегмента («звезда») — сшивание не делается, а все «висячие»
    врезковые концы отвязываются в `type: 'free'`.
- **Проверка (фактическая, прогон функции в Node)**:
  - базовый случай `A—tap1` + `tap1—B` → на выходе **1 сегмент** `free(0) → free(20)`;
  - сегмент между ДВУМЯ врезками (удаляем одну) → 1 сегмент, второй корректно отвязан;
  - «звезда» (3 сегмента на одной врезке) → сшивание не выполняется (3 сегмента,
    концы отвязаны) — ожидаемо, 3 ребра в одно не сливаются.
  - `npm run build` (`built in 4.21s`, 270 модулей) и `npm run lint` — без ошибок.

## [Этап 12] Врезка разрезает сегмент И делит трубопровод на два

- **Требование**: врезка служит разделением трубопровода. Если есть трубопровод из
  нескольких сегментов и на один из них ставится врезка, то получаются ДВА независимых
  трубопровода: часть до врезки и часть после. Если затем достроить трубопровод с
  другой стороны до врезки — третий трубопровод.
- **Было**: `addTap` лишь добавлял точку поверх ребра — сегмент не разрезался,
  `pipelineId` оставался общим (трубопровод не делился).
- **Решение**:
  - новый модуль `features/map/splitSegmentByTap.ts` (чистые функции):
    - `splitSegmentByTap(segments, segId, tapId, leftId, rightId, vidL, vidR)` —
      заменяет сегмент двумя: `left` (from → врезка) и `right` (врезка → to), оба с
      концом `type: 'tap'`; возвращает также список сегментов «левой» стороны;
    - `computePipelineGroups(segments, segId)` — делит сегменты одного трубопровода
      на группы относительно разрезаемого: соединённые с его `from` (left) и с `to` (right);
  - `addTap` теперь: создаёт врезку → режет сегмент → если у сегмента был `pipelineId`,
    «правая» группа сегментов (+ новый `right`) получает НОВЫЙ `pipelineId`, а старая
    запись трубопровода уменьшает `segmentCount`; в дерево добавляется новая запись.
- **Проверка (прогон функций в Node)**: трубопровод `s1:0-10, s2:10-20, s3:20-30`,
  врезка на `s2` → `computePipelineGroups(s2) = {left:[s1], right:[s3]}`;
  `splitSegmentByTap(s2)` → 4 сегмента `s1, s2L[free→tap], s2R[tap→free], s3`.
  Т.е. часть до врезки (`s1`, `s2L`) — старый трубопровод; часть после (`s2R`, `s3`) —
  новый. `npm run build` (383.50 kB) и `npm run lint` — без ошибок.
- **Примечание**: удаление врезки по-прежнему сшивает сегменты обратно
  (`healRemovedTaps`); слияние записей трубопроводов при этом пока не выполняется —
  остаются две записи в дереве (потенциальная доработка).
